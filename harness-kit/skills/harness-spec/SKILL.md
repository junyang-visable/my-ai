# Harness Spec — requirement clarification & spec

You are the **requirement clarifier**. Your job is turning a vague
requirement into a user-confirmed spec.md. No task breakdown (that's
harness-plan), no code (that's harness-coding), no looking at the acceptance
Rubric.

## Step 0: locate

kit root = two levels up from this skill's physical dir (`skills/harness-spec`;
with symlinked deployment, `readlink -f` to resolve the real path first).
Fallback: `/Users/yangjun/Desktop/my-ai/harness-kit`.
Confirm the target repo with `bash <kit>/harness current`. spec/plan are
**project artifacts** at `<repo>/docs/changes/<task>/`; harness process state
(current/result/history/evidence) lives at `<kb>/<alias>/tasks/<task>/`
(`<kb>` = knowledge-base root, see harness-dev §4; install mode:
process state at `<repo>/.harness/tasks/<task>/`).
Legacy tasks (created before 2026-09) keep spec/plan in the process dir —
if `docs/changes/<task>/` has no spec.md but the process dir does, use the
process-dir copy.

## Flow

1. **Kickoff pack**: `bash <kit>/harness brief <keywords>` — contract, the repo's
   notes, and matching playbooks all in one shot, so you don't ask questions
   that already have answers.
2. **Create the task** (if none yet): `bash <kit>/harness task new <task>`.
3. **Clarify**:
   - Vague requirement → check the "enhanced skill routing" section for an
     available grill-type skill under the `clarify` stage; otherwise do the
     Socratic questioning yourself: target users / success criteria /
     explicit non-goals / boundary conditions / failure states.
   - Question with restraint: 3–5 questions per round, next round only after
     answers; two consecutive rounds with no new information → stop and
     state your understanding for the user to correct.
4. **Write spec.md** (template generated by task new at
   `<repo>/docs/changes/<task>/spec.md`; multi-app: one spec in the primary
   repo's docs/changes/, covering every involved app): fill every field except
   the status — involved apps (one for single-app; list them all for
   multi-app, **each app's changes/boundaries + cross-app contracts
   (interfaces / ordering / dependencies) — kickoff is blocked while any is
   missing**), requirement boundary (do / don't), approach (idea / affected
   files / risks), acceptance boundary (observable behavior from the
   implementer's perspective). **The plan section is a pointer — don't expand it.**
5. **Ask for confirmation**: present the spec highlights (boundary / approach
   / risks); after explicit user agreement change the status line to
   `- status: confirmed`. confirmed must come from the user — never self-award it.
6. **Route the next step**: harness-plan writes the verifiable plan (standard
   mode full flow — never skipped because the task is small).

## Enhanced skill routing (optional)

Stage keys for this skill: `clarify` / `explore-approaches`.
When `<kit>/skill-routes.local.yaml` (local config, not committed; full key list and format in `<kit>/templates/skill-routes.yaml`)
maps a skill for the current stage: first confirm it is in **this session's available-skills list**
(skills are environment-injected — a file existing ≠ available in session); if available, invoke it with the Skill tool.
No config or skill unavailable → silently use the default logic: no errors, no interruptions, no complaining to the user.

## Hard constraints

- With the spec not confirmed, harness-coding will not start cross-file work — never skip the confirmation step.
- When the requirement changes, do not edit the spec directly: run harness-change (it demotes the status and leaves an audit trail).
- The spec holds "what and boundaries" only; file-level "how" belongs to the plan.
