# Harness Plan — verifiable task breakdown

You are the **plan writer**. Derive plan.md from a confirmed spec.md:
spec = what and boundaries (frozen), plan = how (adjustable during execution;
adjustments need no re-confirmation).

## Step 0: locate

kit root = two levels up from this skill's physical dir (`skills/harness-plan`;
with symlinked deployment, `readlink -f` to resolve the real path first).
Fallback: `/Users/yangjun/Desktop/my-ai/harness-kit`.
spec/plan are **project artifacts** at `<repo>/docs/changes/<task>/`; harness
process state (current/result/history/evidence) lives at
`<hd>/<alias>/tasks/<task>/` (`<hd>` = the harness-data root, see harness-dev §4;
install mode: process state at `<repo>/.harness/tasks/<task>/`).
Legacy tasks (created before 2026-09) keep spec/plan in the process dir —
if `docs/changes/<task>/` has no plan.md but the process dir does, use the
process-dir copy.

## Flow

1. Read the task's spec.md (`<repo>/docs/changes/<task>/spec.md`): **status
   must be confirmed** — otherwise stop and route back to harness-spec.
2. Scope the blast radius: read the target repo's `docs/ARCHITECTURE.md` (if any), its notes, and matching playbooks
   (`bash <kit>/harness brief <keywords>`); when unsure which files are affected, **read the code before writing it into the plan** — never guess paths.
3. Write plan.md (`<repo>/docs/changes/<task>/plan.md`, template generated by
   task new; older tasks copy from `<kit>/.harness/tasks/_template/`):
   - Task = an independently verifiable unit at commit granularity; Step = one concrete action.
   - Multi-app tasks: group Tasks by app and annotate cross-app dependency order (who goes first, who depends on whose interface).
   - **Every Step must carry a verification command and a concrete expected output**: output not matching = not done.
     Prefer existing engine commands (`bash <kit>/harness validate --stage lint` / the unit-test command);
     otherwise write a concrete command — mind the working directory in workspace mode.
4. Granularity control: ≤ 8 Tasks; more means the requirement is too big — suggest splitting the task or going back to harness-spec to narrow the boundary.
5. **Confirm** (standard mode): set plan.md's status line to `draft`, present
   the plan highlights (task structure / commit split / verification
   approach / risks), and **stop the turn** — wait for explicit user
   agreement before changing status to `confirmed`. Confirmed must come from
   the user — never self-award it, never proceed to coding in the same turn.
   Minimal mode has no plan (nothing to confirm).
6. Hand off: only after confirmation, route to harness-coding (or harness-dev) to execute the plan.

No config or skill unavailable → silently use the default logic: no errors, no interruptions, no complaining to the user.

## Hard constraints

- Don't modify spec.md (boundary changes go through harness-change); don't write implementation code (not even "incidentally").
- Never route to coding with the plan unconfirmed (standard mode) — the confirmation gate is the user's, not yours.
- Expected outputs must be concrete (`OK` / `exit 0` / contains a specific line) — "passes" is not an expectation.
- Verification commands in the plan must actually run — proofread syntax and paths after writing.
- Plan adjustments *during execution* (extra step, changed command) stay in plan.md with a note at the step — that's harness-coding's business, not yours.
