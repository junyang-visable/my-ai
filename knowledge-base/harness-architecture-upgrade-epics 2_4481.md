## 后端工程 Harness 架构升级 — Epic 系列

本系列包含 5 个 Epic，按研发生命周期阶段递进，覆盖从需求评审到部署运维的完整链路。每个 Epic 将对应阶段的工作流能力建设与领域知识库建设打包交付，确保"能力建在哪里，知识就沉淀在哪里"。

**对齐公司 KR：** KR1 — AI-Native Delivery。By March 2027, roll out Harness Engineering across FE, App, BE, WA and QA: a six-phase agent lifecycle (plan → build → verify → deploy → monitor → maintain), with an ontology-based Visable knowledge base as the shared foundation for all agents. Achieve +100% overall delivery efficiency; simple tasks and bug fix work in Express mode at +300% or more.

**六阶段生命周期映射：**

| KR 阶段 | 对应 Epic | 核心能力 |
|---------|----------|---------|
| **Plan** | Epic 2（PRD 评审）+ Epic 3（技术方案） | 需求澄清、评审门禁、方案设计、质量卡口 |
| **Build** | Epic 4（编码） | 标准化 Commands、知识库驱动编码、安全合规 |
| **Verify** | Epic 4（Code Review） | 自动预审、Review Commands、经验沉淀 |
| **Deploy** | Epic 5（部署） | 围栏指标、部署前后自动化检查 |
| **Monitor** | Epic 5（监控） | AI 感知监控、三级健康度围栏 |
| **Maintain** | Epic 5（运维） | 工单修复闭环（HITL）、应急 Playbook |
| *基础设施* | *Epic 1（标准化基础）* | *Commands/Rules 规范、本体知识库、Express 模式、使用手册* |

**Express 模式：** 针对简单任务（small bug fix、配置变更、文案修改等），Agent 可跳过部分阶段直接进入 Build 阶段，实现 +300% 效率提升。Express 模式的触发条件和可跳过的阶段由 Epic 1 统一定义。

**整体依赖关系：** Epic 1 → Epic 2 / Epic 3 → Epic 4 → Epic 5（Epic 2 与 Epic 3 可并行）

## Epic 1：Harness 工程标准化基础与推广体系

### 问题陈述

当前 Harness 工程在研发生命周期的各阶段缺少标准化的 Commands（类似 addyosmani/agent-skills 的统一操作指令）和统一的护栏 Rules（类似 PStack 的始终生效约束），导致团队不同成员使用效果参差不齐，部分成员甚至完全没有将 Harness 工程用起来。同时，各环节缺少清晰的产出物定义和质量标准，无法形成"产出物驱动下一环节"的流水线。此外，缺少标准化的使用手册，团队成员缺乏统一的使用入口和操作指引，进一步加剧了采纳率不足的问题。

### 目标

建立 Harness 工程的标准化基础设施，包括统一的 Commands 规范、分层 Rules 体系、各环节通用产出物标准模板、以及面向全团队的使用手册。设计基于本体论（Ontology）的 Visable 知识库架构，作为所有阶段 Agent 的共享知识基础。定义 Express 模式的触发规则，使简单任务可跳过部分阶段实现 +300% 效率提升。使团队每个成员能够以统一的方式使用 Harness，并为后续各阶段能力建设提供一致的"语言"和"管道"。

### 生命周期定位

本 Epic 不属于六阶段（plan → build → verify → deploy → monitor → maintain）中的任何单一阶段，而是六阶段共同的基础设施层。所有阶段的 Commands、Rules、知识加载和 Express 模式路由均由本 Epic 定义。

### 范围

**1. 标准化 Commands 规范**

- 定义 Commands 的标准格式、命名规范、触发方式和元数据（name, description, version）
- 参考 addyosmani/agent-skills 和 PStack 的 Commands 设计模式，结合团队实际研发生命周期设计 Commands 体系
- Commands 按研发生命周期阶段分类组织（需求评审、技术方案、编码、Code Review、部署、运维）
- 明确 Commands 与现有 Skills（SKILL.md）的关系和协作模式

**2. 分层 Rules 体系**

- 定义 Rules 的分层模型：always-on Rules（始终生效的全局约束）vs on-demand Rules（按阶段/场景按需加载）
- 参考 PStack 的 Rules 设计原则，定义 Rules 的编写规范、优先级和冲突解决机制
- 建立 Rules 与 Commands 的关联关系：Commands 执行时自动加载对应 Rules
- 明确 Rules 与现有 `.cursor/rules/` 的迁移和整合策略

**3. 通用产出物标准模板**

- 定义研发生命周期各环节的产出物清单（PRD 评审报告、技术方案文档、Code Review 报告、部署检查单等）
- 为每种产出物设计标准模板，明确必填章节、质量要求和评审标准
- 定义产出物之间的驱动关系：上游产出物是下游环节的输入，通过产出物状态驱动流程流转
- 定义 Human-in-the-loop 审核节点：每个产出物在自动化流转前需经过人工审核确认
- 设计产出物质量从人工审核逐步过渡到自动化驱动的演进路径

**4. 知识库自动加载与强制引用机制**

- 设计知识库在各阶段 workflow 中的自动注入机制：Agent 执行到特定阶段时，自动加载该阶段对应的领域知识，无需用户手动指定
- 建立"强制引用"约束：Agent 在生成产出物时，必须引用已加载的领域知识作为依据，避免脱离领域上下文的泛泛输出
- 解决当前"很多人没有把知识库用起来"的问题 — 通过 workflow 编排层面的强制机制，让知识库的使用对用户无感

**5. 标准化使用手册**

- 编写面向全团队的使用手册，覆盖：Harness 工程是什么、如何安装配置、各阶段如何使用、常见问题 FAQ
- 提供快速上手指南（Quick Start），降低首次使用门槛
- 包含各角色（工程师、Tech Lead、PM）的使用场景和操作指引
- 手册本身作为 Harness 工程的一部分纳入版本管理

**6. 基于本体论（Ontology）的知识库架构设计**

- 设计 Visable 知识库的统一本体模型：定义核心实体类型（业务概念、业务流程、数据指标、领域模型、系统组件、API 接口等）、实体间关系（依赖、调用、包含、映射等）和属性规范
- 本体模型作为所有领域知识的共享基础架构，确保不同领域的知识可以被 Agent 跨领域关联和推理
- 定义各阶段知识在本体模型中的映射关系：Plan 阶段加载业务概念/流程/指标，Build 阶段加载领域模型/安全合规/Code Graph，Verify 阶段加载回归测试用例，Deploy/Monitor/Maintain 阶段加载围栏指标/应急 Playbook/线上案例
- 本体模型需兼容现有 `knowledge/` 目录的 markdown 文档格式，支持渐进式迁移 — 不要求一次性重构所有现有知识
- 本体模型是 KR1 中"ontology-based Visable knowledge base as the shared foundation for all agents"的直接交付

**7. Express 模式规则定义**

- 定义 Express 模式的触发条件：基于任务复杂度自动判断（小 bug fix、配置变更、文案修改、单文件改动等）或用户显式指定
- 定义 Express 模式下可跳过的阶段：例如跳过 Plan（PRD 评审 + 技术方案）直接进入 Build，或跳过 Verify 的完整预审走轻量 Review
- 定义 Express 模式的不可跳过约束：无论多简单的任务，安全合规 Rules 和核心质量检查始终生效（always-on Rules 不可被 Express 模式绕过）
- 定义 Express 模式的产出物精简规则：哪些产出物可以简化或省略
- Express 模式是实现 KR1 "+300% 效率提升（simple tasks and bug fix）"的关键机制

### 关键产出物

| 产出物 | 说明 |
|--------|------|
| Commands 规范文档 | Commands 标准格式、命名规范、分类体系、与 Skills 的协作模式 |
| Rules 分层规范文档 | Rules 分层模型、编写规范、优先级机制、与现有 `.cursor/rules/` 的整合方案 |
| 通用产出物模板集 | 各环节产出物的标准模板和质量要求 |
| 知识库自动加载机制设计 | 知识注入的 workflow 编排方案和强制引用约束规则 |
| 本体模型（Ontology）设计文档 | 统一本体模型：实体类型、关系定义、属性规范、各阶段知识映射 |
| Express 模式规则文档 | 触发条件、可跳过阶段、不可绕过约束、产出物精简规则 |
| 使用手册 | 面向全团队的标准操作手册，含快速上手指南和各角色指引 |

### 依赖关系

- 无前置依赖（本 Epic 是后续所有 Epic 的基础）
- 需与现有 Team Plugins（visable-be-ai / vcn-be-ai）和 Hooks 机制兼容

### 利益相关方

| 角色 | 关注点 |
|------|--------|
| 后端工程师（16人，4 Groups） | 使用门槛是否足够低，是否增加额外工作量 |
| Harness 架构师 | 规范的可扩展性和一致性 |
| Engineering Leadership | 团队采纳率和使用效果的一致性 |

## Epic 2：PRD 评审阶段能力建设

### 问题陈述

当前团队有 Product Manager 产出 PRD，但 PRD 质量参差不齐，且 PRD 评审沟通效率低。研发人员在开发过程中经常需要反复与 PM 讨论需求细节，原因是需求阶段的疑问、不合理设计和潜在风险没有在评审环节被充分识别和解决。当前 Harness 工程的 workflow 中没有"PRD 评审"这一阶段，缺少结构化的评审流程、评审 checklist 和 Accept 门禁。同时，评审过程缺少业务知识支撑 — 评审人员无法快速获取相关的业务概念定义、业务流程全景、领域数据指标含义等上下文信息，导致评审深度不足。

### 目标

将"PRD 评审"作为研发生命周期的正式阶段纳入 Harness workflow，建设 AI 驱动的 PRD 评审能力。AI 能够自主判断 PRD 的复杂度并路由到对应的评审流程，辅助评审人员完成疑问澄清、不合理设计识别和风险发现。PRD 被 Accept 后形成产出物门禁，驱动后续研发阶段执行，避免开发过程中的反复沟通。

### 生命周期定位

对应 KR1 六阶段中的 **Plan** 阶段。本 Epic 建设的能力直接决定 Plan 阶段的效率和质量 — PRD 评审的充分性影响后续所有阶段的返工率。Express 模式下，小需求可走轻量评审流程（由 Epic 1 定义的 Express 规则控制）。

### 范围

**1. PRD 评审 Workflow 集成**

- 在现有 7 阶段 workflow 之前新增"Phase 0：PRD 评审"阶段
- 定义 PRD 评审的触发条件、输入（PRD 文档）和输出（PRD 评审报告 + Accept/Reject 决策）
- 设计 AI 驱动的 PRD 复杂度自动判断机制：AI 根据 PRD 内容自动评估需求复杂度（重大需求 / 一般需求 / 小需求），并路由到对应的评审流程：
  - 重大需求：完整评审流程（全量 checklist + 多方评审 + 正式 Accept 会议）
  - 一般需求：标准评审流程（核心 checklist + 相关方评审）
  - 小需求：轻量评审流程（快速 checklist + 单人确认）
- 定义 PRD Accept 门禁：只有评审通过的 PRD 才允许进入后续研发阶段

**2. PRD 评审 Checklist**

- 建立结构化的评审 checklist，覆盖三个核心维度：
  - 疑问澄清：识别 PRD 中表述不清、存在歧义或缺失的信息
  - 不合理设计识别：识别逻辑矛盾、边界条件遗漏、与现有系统/流程冲突的产品设计
  - 风险识别：识别技术可行性风险、性能风险、安全风险、合规风险等
- Checklist 与领域知识联动：评审时自动加载业务概念和流程知识，辅助 AI 发现与现有业务逻辑不一致的设计

**3. PRD 评审报告模板**

- 设计标准化的 PRD 评审报告模板，记录：评审结论（Accept/Reject/Conditional Accept）、各 checklist 项的评审结果、遗留问题和待讨论项、评审参与人和时间
- 评审报告作为正式产出物纳入 specs/ 管理

**4. 对应知识库建设**

- 业务概念知识库：梳理各领域的核心业务概念定义、术语表、概念之间的关系
- 业务流程知识库：梳理各领域的核心业务流程（含流程图），标注关键节点和分支条件
- 领域数据指标知识库：梳理各领域的关键业务指标定义、计算口径、数据来源和指标间的关联关系
- 以上知识按照 Epic 1 定义的本体模型（Ontology）进行结构化组织，确保业务概念、流程、指标之间的语义关联可被 Agent 跨领域查询和推理
- 知识沉淀在 `knowledge/` 目录，并在 PRD 评审阶段被 workflow 自动加载

### 关键产出物

| 产出物 | 说明 |
|--------|------|
| PRD 评审 workflow 设计文档 | Phase 0 的完整流程定义，含复杂度路由规则 |
| PRD 评审 checklist | 三维度结构化 checklist（疑问 / 不合理设计 / 风险） |
| PRD 评审报告模板 | 标准化评审报告模板 |
| PRD Accept 门禁规则 | Accept/Reject 的判定标准和流转规则 |
| 业务概念知识库 | 各领域核心业务概念、术语表 |
| 业务流程知识库 | 各领域核心业务流程图及关键节点说明 |
| 领域数据指标知识库 | 关键业务指标定义、计算口径、数据来源 |

### 依赖关系

- 依赖 Epic 1 的 Commands 规范、Rules 体系和产出物模板标准
- PRD 评审 workflow 需与 Product Manager 协作，PM 需了解并配合评审流程

### 利益相关方

| 角色 | 关注点 |
|------|--------|
| Product Manager | 评审流程是否增加 PM 的工作负担，评审反馈是否建设性 |
| 后端工程师 | 评审是否能真正减少开发中的反复沟通 |
| Harness 架构师 | 评审 workflow 与现有 7 阶段 workflow 的无缝集成 |

## Epic 3：技术方案设计阶段能力建设

### 问题陈述

当前团队不同成员产出的技术方案文档质量参差不齐，缺少统一的质量标准和评审门禁。技术方案的设计过程缺少领域知识支撑 — 工程师和 AI 在设计方案时，无法快速获取领域模型定义、系统间调用链路、历史方案参考等关键上下文，导致设计方案可能遗漏关键约束或重复造轮子。同时，技术方案的评审缺少结构化标准，评审质量依赖评审人的个人经验和状态。

### 目标

建立技术方案设计阶段的标准化能力，包括技术方案文档标准模板、质量评审标准和门禁卡口。通过 AI 辅助提升技术方案的设计质量和评审效率，确保技术方案在领域模型、系统架构和历史经验方面具备充分的上下文支撑。技术方案通过质量门禁后形成产出物，驱动下游编码执行。

### 生命周期定位

对应 KR1 六阶段中的 **Plan** 阶段（与 Epic 2 共同构成 Plan 阶段的两个子阶段：需求评审 → 技术方案设计）。Express 模式下，小需求的技术方案可走简化模板（由 Epic 1 定义的 Express 规则控制）。

### 范围

**1. 技术方案文档标准模板**

- 设计技术方案文档的标准结构，明确必填章节：背景与目标、方案设计（含架构图）、领域模型变更、接口设计、数据模型变更、兼容性分析、性能评估、风险与降级策略、测试策略、上线方案
- 定义每个章节的质量要求（如"兼容性分析"必须覆盖向后兼容、数据迁移、灰度方案三个子项）
- 模板与 Epic 1 的通用产出物标准对齐

**2. 质量评审标准与门禁卡口**

- 建立技术方案的质量评审 checklist，覆盖：方案完整性、架构合理性、领域模型一致性、接口设计规范性、性能与可扩展性、安全与合规、可测试性、可运维性
- 定义质量门禁的通过标准：哪些项为 Must Pass（不通过则打回），哪些为 Should Pass（可带条件通过）
- 设计 AI 辅助评审机制：AI 根据 checklist 自动扫描技术方案文档，生成预审报告，标注潜在问题供人工评审参考
- 门禁卡口与 workflow 集成：技术方案通过门禁后才允许进入编码阶段

**3. 对应知识库建设**

- 领域模型知识库：梳理各领域的核心领域模型（实体、值对象、聚合根）、模型之间的关系和约束规则
- 系统间调用链路架构知识库：梳理各领域涉及的系统间调用关系（上游/下游）、通信协议、数据流向、SLA 约束
- 历史技术方案参考库：归档过往高质量的技术方案文档，作为新方案设计的参考基线
- 以上知识按照 Epic 1 定义的本体模型（Ontology）进行结构化组织，确保领域模型与系统调用链路之间的关联可被 Agent 在方案设计时自动引用
- 知识沉淀在 `knowledge/` 目录，并在技术方案设计阶段被 workflow 自动加载

### 关键产出物

| 产出物 | 说明 |
|--------|------|
| 技术方案文档标准模板 | 含必填章节定义和各章节质量要求 |
| 技术方案质量评审 checklist | 结构化 checklist，区分 Must Pass / Should Pass |
| 质量门禁卡口规则 | 通过标准和流转规则 |
| AI 辅助预审机制 | AI 自动扫描技术方案并生成预审报告 |
| 领域模型知识库 | 各领域核心领域模型定义 |
| 系统间调用链路架构知识库 | 系统间调用关系、协议、数据流、SLA |
| 历史技术方案参考库 | 高质量历史方案归档 |

### 依赖关系

- 依赖 Epic 1 的 Commands 规范、Rules 体系和产出物模板标准
- 领域模型和调用链路知识的梳理需要各领域 Tech Lead 参与

### 利益相关方

| 角色 | 关注点 |
|------|--------|
| 后端工程师 | 模板是否过于繁琐，是否影响设计效率 |
| Tech Lead | 评审标准是否可操作，门禁是否会成为瓶颈 |
| Harness 架构师 | 知识库的维护成本和时效性 |

## Epic 4：编码与 Code Review 阶段能力建设

### 问题陈述

当前编码和 Code Review 阶段缺少标准化的 Commands 来指导 AI 辅助实现和审查。团队在研发过程中经常遇到 AI 产出的代码或 Review 意见不符合预期，需要多轮澄清和反复尝试，但这些经验教训没有持续、自动化地沉淀到 Harness 工程中。现有的 3-Strike 经验沉淀机制缺少对沉淀物质量的回检，可能沉淀错误经验导致质量退化。此外，缺少安全合规知识、Code Graph（代码关系理解）和领域回归测试用例知识，导致 AI 编码时 Token 消耗大、合规意识弱、测试覆盖不足。

### 目标

建立编码和 Code Review 阶段的标准化 Commands 体系，实现经验的自动沉淀与质量回检闭环。建设安全合规知识库、Code Graph 和回归测试用例知识库，提升 AI 编码的准确性、合规性和效率。通过经验自动沉淀机制，使 Harness 工程在编码和 Review 场景中越用越聪明。

### 生命周期定位

对应 KR1 六阶段中的 **Build**（编码）和 **Verify**（Code Review）两个阶段。本 Epic 是六阶段中 Token 消耗最大、使用频率最高的环节，Code Graph 和知识库自动加载直接决定 AI 编码的效率和质量。Express 模式下，简单任务可跳过完整预审走轻量 Review（由 Epic 1 定义的 Express 规则控制）。

### 范围

**1. 编码阶段标准化 Commands**

- 设计编码阶段的 Commands 集：需求理解 Command（加载 PRD + 技术方案上下文）、代码实现 Command（按领域规范和约束生成代码）、单元测试 Command（基于回归测试用例知识库生成测试）、自测检查 Command（运行 lint/typecheck/test 并生成自测报告）
- 每个 Command 执行时自动加载对应阶段的 Rules 和 Knowledge
- Commands 与 Epic 1 定义的规范保持一致

**2. Code Review 阶段标准化 Commands**

- 设计 Code Review 阶段的 Commands 集：自动预审 Command（AI 根据 review-checklist.md 自动扫描 MR/PR，生成预审报告）、人工 Review 辅助 Command（为人工 Reviewer 标注重点关注区域）、Review 意见生成 Command（生成结构化的 Review 意见，区分 Must Fix / Should Fix / Suggestion）
- Review 意见自动关联对应的 Rules，确保 Review 标准的一致性

**3. 经验自动沉淀与质量回检机制**

- 完善现有 3-Strike 机制：当同一问题在 experience-index.md 中出现 ≥ 3 次时，自动触发沉淀提案（新增 Rule / Skill / Workflow 调整），经用户确认后执行
- 新增沉淀物质量回检机制：定期对已沉淀的 Rules/Skills 进行质量审查，识别可能因误判或上下文变化而失效的沉淀物，标记为待复核或自动清除
- 沉淀过程对用户无感：在正常的编码和 Review 工作流中自动完成经验捕获，不需要用户额外操作

**4. 安全合规知识库**

- 梳理团队的安全合规要求：输入验证、XSS/CSRF 防护、敏感数据处理、认证授权规范、依赖安全等
- 以结构化 Rules 和 Knowledge 形式沉淀，按照 Epic 1 定义的本体模型组织，在编码和 Review 阶段被自动加载
- 确保 AI 生成的代码和 Review 意见自动遵循安全合规约束

**5. Code Graph（代码关系理解）**

- 建设代码关系的结构化理解能力：模块依赖图、核心接口调用链、数据模型关联关系
- 目标：降低 AI 编码和 Review 时的 Token 消耗 — 通过 Code Graph 精准定位相关代码上下文，避免全量 grep 和盲目扫描
- Code Graph 按照 Epic 1 定义的本体模型中的系统组件和 API 接口实体进行组织，与领域模型知识库形成关联
- Code Graph 知识沉淀在 `knowledge/` 目录，编码和 Review Commands 执行时按需加载

**6. 领域回归测试用例知识库**

- 梳理各领域的核心回归测试用例：关键业务场景、边界条件、历史 bug 复现场景
- 按照 Epic 1 定义的本体模型组织，建立测试用例与业务流程、领域模型之间的语义关联
- 知识沉淀在 `knowledge/` 目录，编码阶段生成单元测试和 Code Review 阶段评估测试覆盖时自动引用

### 关键产出物

| 产出物 | 说明 |
|--------|------|
| 编码阶段 Commands 集 | 需求理解、代码实现、单元测试、自测检查 |
| Code Review 阶段 Commands 集 | 自动预审、人工 Review 辅助、Review 意见生成 |
| 经验沉淀质量回检机制 | 沉淀物定期审查和清理流程 |
| 安全合规知识库 | 安全编码规范、合规要求、检查规则 |
| Code Graph 知识 | 模块依赖图、核心接口调用链、数据模型关联 |
| 领域回归测试用例知识库 | 关键业务场景测试用例集 |

### 依赖关系

- 依赖 Epic 1 的 Commands 规范、Rules 体系和知识库自动加载机制
- 依赖 Epic 2 的 PRD 评审产出物和 Epic 3 的技术方案产出物作为上游输入
- Code Graph 建设可能需要应用仓库的代码索引工具支持

### 利益相关方

| 角色 | 关注点 |
|------|--------|
| 后端工程师 | Commands 是否真正提升编码效率，Token 消耗是否明显降低 |
| Tech Lead | Review 标准的一致性，沉淀物质量是否可控 |
| Harness 架构师 | 3-Strike 机制的可靠性，Code Graph 的维护成本 |

## Epic 5：部署运维阶段能力建设

### 问题陈述

当前变更发布的部署阶段和发布后的运维阶段缺少清晰的围栏指标和监控能力来自动化识别和拦截问题。系统、应用、业务三个层级的健康度缺少统一定义，AI 无法感知线上异常，问题发现和修复完全依赖人工巡检和告警响应。同时，运维阶段缺少结构化的知识支撑 — 线上问题的历史案例、根因分析和修复方案散落在各处，应急 Playbook 覆盖不全，导致问题恢复时间长、重复问题反复消耗人力。

### 目标

建立部署运维阶段的围栏指标体系和 AI 可感知的监控能力。AI 能够自动发现线上异常并创建 Jira 问题工单，经人工确认后驱动 AI 分析根因并制定修复方案，再经人工审批后执行修复 — 形成"AI 感知 → 工单驱动 → 人工确认 → AI 分析 → 人工审批 → AI 执行"的完整闭环。同时建设运维阶段的知识库，使 AI 的问题分析和修复能力持续增强。

### 生命周期定位

对应 KR1 六阶段中的 **Deploy**（部署）、**Monitor**（监控）和 **Maintain**（运维）三个阶段。本 Epic 覆盖生命周期的最后三个环节，是系统上线后稳定性和安全性的保障。Express 模式不适用于本 Epic 的阶段（部署和运维阶段始终需要完整的围栏检查和 HITL 流程）。

### 范围

**1. 三级健康度围栏指标定义**

- 系统级围栏：基础设施层指标（CPU/内存/磁盘/网络、ECS 实例健康、ELB 状态、WAF 告警）
- 应用级围栏：应用层指标（请求延迟 P50/P95/P99、错误率、吞吐量、Datadog APM 健康状态、部署变更状态）
- 业务级围栏：业务层指标（关键业务流程成功率、订单转化率、搜索命中率、同步任务完成率等 — 按领域定义）
- 每级围栏定义清晰的阈值和告警规则，区分 Warning / Critical / Blocker 三级

**2. AI 可感知的监控体系**

- 集成 Datadog 监控能力：定义标准化的 Datadog 查询模板（T+0 实时）和 Redash/dbt 指标定义（T+1 离线），使 AI 能够通过 MCP 工具查询系统健康状态
- 建设变更发布阶段的自动化检查：部署前自动检查围栏指标是否满足发布条件，部署后自动验证服务健康度
- 异常自动发现：AI 定期（或通过事件触发）扫描三级围栏指标，自动识别异常模式

**3. AI 驱动的工单修复闭环（全流程 HITL）**

- 问题发现阶段：AI 自动发现异常 → 创建 Jira 问题工单（含异常描述、影响范围、相关指标快照）
- 人工确认阶段：等待人工确认问题真实性，排除误报
- 根因分析阶段：人工确认后，AI 自动分析根因（结合日志、trace、变更记录、历史案例知识库），生成根因分析报告
- 修复方案阶段：AI 基于根因分析制定修复方案（含修复步骤、回滚方案、影响评估），提交人工审批
- 修复执行阶段：人工审批通过后，AI 驱动修复执行（通过工单状态流转跟踪执行进度）
- 关键约束：每一步都需要人工确认/审批后才进入下一步，AI 不自主执行任何生产环境变更

**4. 对应知识库建设**

- 线上问题案例库：结构化归档历史线上问题（症状 → 根因 → 修复方案 → 复盘教训），AI 分析新问题时自动检索相似案例
- 应急 Playbook：按问题类型（性能劣化、数据不一致、第三方依赖故障等）编写标准应急操作手册
- Datadog 查询模板库：标准化的实时/离线指标查询模板，AI 通过 MCP 工具直接查询
- 以上知识按照 Epic 1 定义的本体模型（Ontology）进行结构化组织，建立线上问题与应用组件、业务流程之间的语义关联，使 AI 能基于系统拓扑快速定位影响范围
- 知识沉淀在 `knowledge/` 目录（`stability.md` + `reference/`），并在运维阶段被 workflow 自动加载

### 关键产出物

| 产出物 | 说明 |
|--------|------|
| 三级健康度围栏指标定义 | 系统级 / 应用级 / 业务级围栏指标和阈值 |
| Datadog 查询模板集 | T+0 实时 + T+1 离线标准化查询模板 |
| AI 驱动的工单修复闭环 workflow | 完整的 HITL 流程定义（6 阶段，4 个人工确认点） |
| 线上问题案例库 | 历史问题的结构化归档 |
| 应急 Playbook | 按问题类型的标准应急操作手册 |
| 部署前后自动化检查机制 | 部署前围栏检查 + 部署后健康度验证 |

### 依赖关系

- 依赖 Epic 1 的 Commands 规范、Rules 体系和知识库自动加载机制
- 依赖 Datadog MCP 工具的可用性
- 依赖 Jira 工单系统的集成（Atlassian MCP）
- 三级围栏指标的定义需要各领域 Tech Lead 和 SRE 协作

### 利益相关方

| 角色 | 关注点 |
|------|--------|
| 后端工程师 | 告警是否精准，工单流程是否增加额外负担 |
| Tech Lead | 围栏指标是否覆盖关键业务场景 |
| Engineering Leadership | 问题发现到修复的平均时间（MTTR）是否改善 |
| Harness 架构师 | AI 感知能力的技术可行性，HITL 流程的效率平衡 |
