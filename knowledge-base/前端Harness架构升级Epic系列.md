## Epic FE-1：架构熵治理 — 熵检测常态化与度量闭环

### 问题陈述

现有门禁拦不住 AI slop：lint 查"语法与风格对不对"、E2E 查"功能通不通"、CR 查"设计合不合理"，而 AI 产出的复述式注释、防御性兜底、过早抽象等熵增模式单看都是"合法代码"。熵检测能力 slop-linter（双层检测：确定性规则 + 语义审查）待建设；已建成的 cr-frontend（PR 评审）与熵检测的分工边界未成文；熵治理六道防线中第 6 道（度量闭环）完全空白——"每次变更不熵增"的目标没有数字支撑。

### 目标

建设 slop-linter 双层熵检测能力，并推进到"每次变更必经、可度量、规则自演进"的常态化防线：建成并验收 slop-linter，将熵治理与 cr-frontend 评审能力收敛为统一 Linter Agent 对外呈现，建立熵度量台账，跑通规则演进首轮闭环。

### 范围

**1. slop-linter 建设与全流程验收（P0）**

- 按[设计篇](https://visable.atlassian.net/wiki/spaces/~71202075c2285d8115445a8b9dc5244bebf36f/pages/720928831)定稿方案实现双层检测：确定性规则引擎（机械层，可精确匹配的模式）+ AI 语义审查（语义层，需理解意图的模式）；只对本次变更行计分，存量问题降 advisory
- 目标仓库零侵入；修复循环有界（≤3 轮、出口双查、不自动 commit）；漏判误判经"提议-确认"闸门回写规则
- 真实需求收尾后跑全流程验收：显式传入目标仓库与基线分支（repo/base）、报告三档呈现、修复循环、lessons 回写
- 兜底：业务节奏拖太久时，用近期已合 PR 的历史 diff 补跑验收

**2. 统一 Linter Agent：熵治理 × cr-frontend 融合呈现（P1）**

- 将架构熵治理与 cr-frontend 的评审能力收敛为一个 Linter Agent 对外呈现：一次调用同时完成 PR 评审（变更分类、回归清单、专项评估）与熵检测（变更行计分、verdict），输出一份合并报告
- 对使用者只暴露"一个 linter"入口；内部保持 cr-frontend 评审工作流与 slop-linter 双层检测两个引擎，评审结论与熵检测结果去重后合并
- 验收：一次调用产出统一报告、无重复条目；结论可分别落 review.md / verification.md 工件

**3. 数据收集与统计：熵度量台账（P0）**

- 指标：每需求 error 级 / advisory 级 findings 数、修复轮次、语义层命中 Top5 规则、PR diff 中位数、检出后复发数
- 落点：随任务收尾记录沉淀（任务目录内），4~6 周回看后再决定是否可视化
- 验收：连续 4 周有数据，能回答"熵增是否被压住"

**4. 自我更新成长：规则演进与毕业机制（P1）**

- 检测教训经"提议-确认"闸门回写规则库：过严 / 误报多的规则调级，rejected 段记录拒绝案例
- 语义层高频命中规则"毕业"为机械层确定性规则——检查硬度随使用增强
- 首轮验收：毕业 / 调级 / 拒绝各至少 1 例，规则变更 commit 留痕

**5. 推广（P2）**

- 前置：范围 1 验收与范围 2 统一 Linter Agent 完成
- 1~2 位同事试用统一 Linter Agent，收集上手门槛反馈

### 关键产出物

| 产出物 | 说明 |
|--------|------|
| slop-linter 全流程验收记录 | 真实 diff 全链路走通证据（含修复循环与 lessons 回写） |
| 熵度量台账 | 每需求 findings、修复轮次、diff 中位数，按周回看 |
| 规则演进记录 | 毕业 / 调级 / 拒绝案例留痕，规则库随使用演进 |
| 统一 Linter Agent | 熵治理 × PR 评审的单一入口与合并报告 |

## Epic FE-2：稳定性防线 — 告警覆盖收尾、三级围栏与知识沉淀

### 问题陈述

FE-1066 专项（计划新建 Sunfire 48 + Datadog 30 条，09-07 口径）收尾未完：部分 Datadog JSON 未导入、conversations 4 条仍用旧配置、api_error / script_error 阈值未经真实基线校准。三级围栏的业务级（第三层）对前端无定义。线上问题的分析过程散落在排查记录里，未沉淀为可检索案例。

### 目标

完成应用级告警覆盖收尾并按真实基线校准阈值；补齐业务级围栏定义，形成前端三级健康度围栏；建立线上问题案例库与告警能力清单的同步机制。

### 范围

**1. 告警覆盖收尾与阈值校准（P0）**

- 先盘点 FE-1066 条目当前实际状态（09-07 记录后可能已有推进），避免重复建；导入执行方式（控制台手工 vs browser-use 批量）拍板后执行
- 收尾：conversations 4 条旧配置更新、未导入的项目级 + supplier 聚合 JSON 导入、R-04 清理待办
- 阈值校准：告警运行 1~2 周后按真实基线调整——api_error 阈值按项目流量分档，script_error 优先 wow_delta 同比降噪，高价值接口建 is_critical 低阈值子规则
- 验收标准：每条告警能回答"抓到过真问题吗 / 冤枉过系统吗"

**2. 三级围栏 FE 版定义（P2）**

- 系统级（CloudWatch / ECS）与应用级（Datadog 5 条模板）已具备，文档化
- 业务级：关键转化 / 白屏率 / SSR 错误率的业务口径 + Warning / Critical 分级，与产品、后端对齐

**3. 监控知识沉淀（P1）**

- 线上问题案例库：症状 → 根因 → 修复 → 教训；首个案例 business-insights 内存泄漏（22h 周期 OOM、九轮压测定位）
- 告警能力清单 ↔ coverage-diagnosis 能力目录同步机制（告警新增 / 退役时登记）

### 关键产出物

| 产出物 | 说明 |
|--------|------|
| FE-1066 收尾核对表 | 逐条目状态盘点 + 关闭记录 |
| 阈值校准记录 | 各 event_type 实际基线与调整前后对照 |
| 三级围栏 FE 定义 | 系统级 / 应用级 / 业务级指标、阈值、分级 |
| 线上问题案例库 | 结构化案例（症状→根因→修复→教训），首批 ≥1 篇 |

## Epic FE-3：Monitoring Agent 闭环 — 错误分析修复 × 数据采集 × 自成长

### 问题陈述

monitoring-agent 套件五技能（orchestrator / release-guard / coverage-diagnosis / coverage-filter / requirement-guard）已完成第一轮建设：requirement-guard 信号源补齐（Sentry / Datadog 直查）、定时巡检（定时产出巡检报告）、需求级覆盖闭环（诊断→登记→核对→回写）均已从 0 到 1 跑通。当前差距在闭环质量而非覆盖本身：覆盖结论的可信度不足（误报、低置信判定风险），错误场景覆盖度有限（失败模式拆分与筛选条件不全）；异常发现止步于"报告"，缺少错误识别与归因分析能力；最终尚未打通 Jira 工单闭环。

### 目标

把 monitoring-agent 从"跑通闭环"推进到"可信闭环"：先提高覆盖结论的可信度与错误场景覆盖度，再补错误识别与归因分析能力，最终形成"AI 感知 → 工单驱动 → 人工确认 → AI 分析 → 人工审批 → AI 执行"的工单修复闭环（全流程 HITL）。

### 范围

**1. 覆盖可信度与错误场景扩展（P0）**

- 假阳性防护进判定链："0 errors"先核 is_provisional 与 breakdowns / trend 是否为空，空结果不判健康
- 多信号源交叉验证：ODPS × Sentry × Datadog 互证后再出 verdict，单源不可证时降级标注
- 低置信判定强制降级：混合失败模式必拆分、不合并判定；page_id 接线先核实 definePageMeta.virtualPageTitle 链——沿用已验证的两条纠偏纪律
- 错误场景反推补齐：以已发生与高风险错误场景（API 超时、网络异常、资源加载失败、SSR 边界）扩充能力目录与筛选条件
- 与 FE-2 的阈值校准、告警能力清单同步机制联动：新增告警即评估是否入能力目录

**2. 错误识别与分析能力（P1）**

- 巡检 / 覆盖核对发现的异常自动做识别与归因：错误分类、根因假设、影响面评估、证据链组织（日志 / trace / 变更记录 / FE-2 案例库相似案例检索）
- 输出结构化分析简报

**3. 数据收集与统计（P1）**

- 巡检、覆盖诊断、上线核对全过程的运行数据落库：异常检出数、误报 / 漏报、判定置信度、核对时效
- 按周期统计回看，作为可信度优化与阈值校准的输入

**4. 异常 → Jira 工单闭环（P2，下阶段目标）**

- 巡检 / 分析发现异常 → 自动建 Jira issue（异常描述、影响面、指标快照、run_id 证据链）→ 人工确认真实性 → AI 根因分析 → 修复方案人工审批后执行
- 约束：AI 不自主执行任何生产变更（HITL 原则）；闭环建成前异常止步于分析简报、不建单
- 前置：建单字段与通知口径拍板

**5. 自我更新成长：知识自动加载与积累（P2）**

- 把 FE-2 案例库、围栏定义、能力目录沉淀在知识库，并由 agent 工作流按阶段自动加载
- 自身运行产出回流知识库：新案例、新筛选条件、误报教训进判定纪律——越用越准
- 根因分析时自动检索相似案例

### 关键产出物

| 产出物 | 说明 |
|--------|------|
| 覆盖可信度判定纪律 | 假阳性防护、多源交叉验证、低置信降级的判定链规则 |
| 错误场景筛选条件扩展 | 新增失败模式的能力目录条目与筛选条件 |
| 错误识别分析简报 | 异常的结构化归因输出 |
| 运行数据统计 | 巡检 / 诊断 / 核对的检出、误报、时效统计 |
| 工单闭环 workflow | HITL 流程定义与 Jira 字段约定 |
| 知识自动加载与积累机制 | 外部知识注入 + 自身运行产出回流 |
